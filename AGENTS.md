## Что значит «готово» утром

Владелец сформулировал два явных требования и одно общее:
1. Десктоп должен реально выглядеть и ощущаться как десктопное приложение — не увеличенная мобильная вёрстка.
2. Ни один компонент с выпадающим списком/попапом не должен ломаться на ПК.
3. Переход в прошлый чат должен работать сам, без ручной перезагрузки страницы.

Инженерно это означает:
1. `npm run typecheck`, `npm run lint`, `npm run test:unit`, `npm run test:integration`, `npm run build`, `npm run perf:budget` — зелёные. (`npm run check` целиком не подходит как единственный критерий — в нём есть `trust:legal`, который падает по причине, не относящейся к тебе, см. «Вне зоны ответственности».)
2. Ты реально открывал приложение мышью и клавиатурой (Playwright, `desktop-chromium`, плюс ручные ширины) на 768, 834, 1024, 1280, 1440 и 1920px, менял ширину окна вживую (drag-resize), а не только смотрел на фиксированные скриншоты — баг с выпадающими списками почти наверняка завязан именно на реальную геометрию окна, а не на код сам по себе.
3. Баг с переключением чатов без перезагрузки — воспроизведён, у него есть объяснённая причина (не «я потыкал и вроде заработало»), есть регрессионный тест.
4. Каждый dropdown/popover/select/menu в приложении явно проверен на десктопных ширинах и внесён в отчёт (список ниже — стартовый, не исчерпывающий).
5. Существующее поведение и мобильная версия не сломаны.

## Конкретные зацепки — с чего начать (проверено лично, с номерами строк)

### Приоритет 1 — три конкретных бага, которые описал владелец

**1. Выпадающее меню вложений ломается на ПК — я нашёл вероятную причину.**

`components/playground/ResponsiveChatComposer.tsx:39`:
```
<div className="w-full [&_[role=menu]]:!bottom-[calc(100%+8px)] [&_[role=menu]]:!top-auto">
```
Это CSS-правило с `!important` жёстко приклеивает ЛЮБОЙ элемент с `role="menu"` внутри композера снизу (`bottom: calc(100% + 8px) !important; top: auto !important`) — **безусловно**, вне зависимости от того, сколько реально места над композером.

А меню вложений в `components/ui/ai-chat-input.tsx:250-297` (плейсмент вычисляется через `getBoundingClientRect` в `useLayoutEffect`, результат — `attachmentMenuPlacement`, `"above"` или `"below"`) и применяется на строке 468 через обычный (не `!important`) класс `bottom-[calc(100%+8px)]` / `top-[calc(100%+8px)]`. JS-логика там написана корректно и учитывает `visualViewport` — но CSS из `ResponsiveChatComposer.tsx:39` перебивает её результат в любом случае, всегда выигрывая по каскаду (`!important` в классе побеждает обычный инлайн-стиль/класс).

На телефоне это почти никогда не заметно — композер обычно и так внизу узкого высокого экрана, там реально почти всегда есть место сверху, так что «свернуть в above» случайно совпадает с правильным ответом. На десктопе, где окно может быть невысоким/широким или композер не в самом низу, JS честно решает «сверху не помещается, ставь снизу» — а CSS всё равно рисует сверху, и меню обрезается/улетает за экран. Это прямое совпадение с описанием «на телефоне всё гуд, на ПК всё ломается».

Что сделать: разберись, зачем вообще появилось это `!important`-правило (вероятно, чтобы что-то не перекрывало виртуальную клавиатуру на мобильном) и сделай его условным — либо ограничь медиа-запросом по touch/узкому экрану, либо убери совсем и доверься уже готовой JS-логике `attachmentMenuPlacement`, либо синхронизируй оба механизма в один источник правды. Добавь Playwright-тест: открой меню вложений в узком по высоте окне (например, 1400×650) на `desktop-chromium` и проверь, что меню полностью в вьюпорте.

**2. `ai-model-select.tsx` — отдельная, самостоятельная проблема с тем же классом симптомов.** Строки 595-631: позиция считается через `getBoundingClientRect`, есть попытка collision handling (флип top/bottom, `maxHeight` от высоты вьюпорта), но: (a) горизонтальный клэмп использует захардкоженную ширину `360` (`viewportWidth - 360 - gutter`), хотя реальная ширина списка — `min-w-56` (224px) плюс контент, при рассинхроне список может вылезать за правый край на узких десктопных окнах; (b) фокус остаётся на триггере, а клавиатурные события (`ArrowUp/Down/Enter/Escape`) слушаются глобально на `document` (строки 418-426 в этом файле) — если на странице открыт ещё один похожий виджет или пользователь просто печатает в другом поле, это может конфликтовать. Проверь на реальной клавиатурной навигации (Tab до триггера, Enter чтобы открыть, стрелки, Escape) на разных ширинах, включи Chrome DevTools responsive mode с реальным resize, не только фиксированные пресеты.

**3. Переключение на прошлый чат требует перезагрузки — нужно найти настоящую причину, не гадать.**

Это сформулировано пользователем как наблюдаемый факт, но я не смог воспроизвести его в статическом чтении кода — воспроизведи в браузере первым делом, это твой приоритет №1 сегодня. Вот что я успел раскопать и где смотреть:

## Как вести ночь — порядок действий

1. **Первые ~20% времени** — воспроизведи находку №3 (перезагрузка чата) и остальные пункты приоритета 1 своими глазами в браузере на реальных ширинах, прежде чем чинить. Заведи свой `AGENT_AUDIT_DESKTOP.md` со списком находок.
2. **Основное время** — чини по приоритету, каждую правку — с `npm run test:unit`/`test:integration` и визуальной проверкой в Playwright на нескольких ширинах сразу (не только 1440px, на котором «обычно всё нормально»).
3. **Последние ~15-20% времени** — полный `npm run check` кроме `trust:legal`; полный Playwright-прогон на `desktop-chromium` и (не ломая) на мобильных профилях, чтобы убедиться, что не задел файлы Claude; отчёт.

## Матрица ручной/автоматической проверки

Ширины: 768, 834, 900 (частый случай — окно не на весь экран), 1024, 1280, 1440, 1920px. Для каждой: живой drag-resize окна браузера (не только заранее заданные пресеты — баги с попапами часто проявляются именно в момент изменения размера), открытие/закрытие каждого dropdown/popover (список: model selector, меню вложений, `<details>`-меню действий в `ConversationArchive.tsx:175-183`, `ChatContextDrawer`, `TrustControlSheet`, языковой и тематический тумблеры), переключение между несколькими сохранёнными диалогами подряд без `F5`, полная клавиатурная навигация (Tab/Shift+Tab/Enter/Escape/стрелки) без мыши, масштаб экрана 125%/150% (частый десктопный сценарий, из-за которого «на глаз всё ок» может обмануть).

## Жёсткие правила

- Никогда не подгоняй тест или бюджет под прохождение вместо исправления причины.
- Не трогай секреты, не коммить `.env.local`.
- Не делай глобальных «мета»-рефакторингов ради вкуса — минимально достаточные, тестируемые изменения, уважающие `docs/ARCHITECTURE.md`.
- Держи двуязычность (ru/en) в синхроне при любых правках текста.
- Не добавляй новых постоянных подписей/пояснений в UI — в проекте действует правило против AI-slop, аудит уже вычистил часть таких подписей, не возвращай их обратно псевдо-desktop-подсказками («наведите курсор», «нажмите здесь» и т.п.).
