3. Ты реально запускал приложение в браузере (Playwright, см. ниже) на ширинах 320–430px и на 768px, в портретной и альбомной ориентации, с открытой и закрытой виртуальной клавиатурой — и ничего не «поехало», не обрезалось, не потерялось.
4. Ты измерил, а не предположил, LCP/CLS/INP/TBT на мобильном эмулированном прогоне. Прошлый аудит (`AGENT_AUDIT.md`) прямо написал, что не смог этого сделать («доступного Chrome DevTools MCP в этой среде нет»). У тебя есть настоящий Chrome на машине пользователя — это единственное, чего не хватало прошлому агенту, и это твоя главная добавленная ценность за ночь.
5. Существующее поведение не сломано: полный набор тестов зелёный, ни один компонент из мобильного UI не исчез и не потерял функциональность по сравнению с текущим состоянием.

## Пересечение с Codex (десктоп) — как не подраться за одни файлы

Codex работает над `components/ui/ai-chat-input.tsx`, `components/ui/ai-model-select.tsx`, брейкпоинтами навигации (`PlaygroundChat.tsx` шапка/сайдбар), `components/playground/HistoryDropdown.tsx`, `components/playground/ConversationArchive.tsx`, `components/playground/ErmaNovaWorkspace.tsx`. Это файлы, которые физически общие для обеих версий (responsive-код, а не отдельные ветки mobile/desktop).

Правила:
- Если тебе нужно поменять что-то в общем файле — меняй только то, что реально влияет на мобильные брейкпоинты (классы вида `sm:`, до `md:`), не трогай десктопные ветки условий (`lg:`, `xl:`) и не переписывай структуру компонента целиком.
- В начале любого коммита, который трогает файл из списка Codex выше, добавь в сообщение коммита пометку `[shared]`, чтобы утром было легко увидеть точки пересечения при слиянии веток.
- Если закончишь свою часть раньше времени — не лезь в файлы Codex «за компанию». Вместо этого углубляйся в свою зону: больше вьюпортов, больше edge cases (медленная сеть, offline, обрезанные шрифты, RTL/локали), больше тестов.
- Слияние `agent/mobile-overnight` и `agent/desktop-overnight` в одну ветку — это утренняя задача владельца продукта, не твоя. Твоя задача — оставить чистую, понятную, самодостаточную ветку.

## Конкретные зацепки — с чего начать (по приоритету)

### Приоритет 1

1. **JS-бюджет и вес сборки.** `AGENT_AUDIT.md` зафиксировал: gzip JS превышает бюджет (437.4 КБ при пределе 429.7 КБ), самый тяжёлый чанк — `rehype-katex` (261.7 КБ). Проверь актуальное состояние (`npm run perf:budget`) — возможно, часть уже поправлена. Если превышение осталось: убедись, что KaTeX (математика/формулы в Markdown) грузится лениво и только когда в ответе реально есть формулы, а не в общем бандле чата. Сначала измерь, потом режь — не режь вслепую.
2. **Глобальные наблюдатели дорого работают во время стриминга.** `components/site/PublicBrandingGuard.tsx:47-54` и `components/site/MotionOrchestrator.tsx:54-59` вешают `MutationObserver` на `document.documentElement`/`body` целиком. Чат постоянно меняет текстовые узлы во время генерации ответа — это может дёргать оба observer'а на каждое обновление на слабых телефонах. Ограничь наблюдение явным контейнером страницы, а не всем документом.
3. **Дублирующиеся деревья mobile/desktop.** `app/page.tsx:34-153` рендерит ДВЕ полные копии главной страницы (`hidden lg:block` и `lg:hidden`), обе с `priority`-картинкой. То же в `app/patch-notes/page.tsx:45` (MobileReleaseBrowser + PatchNotesBrowser одновременно) и в `ResponsiveMessageList.tsx`. Мобильный браузер гидрирует и держит в DOM обе ветки, даже скрытую. Прежде чем резать — проверь, не завязаны ли на `data-device-version`/`data-home-surface` атрибуты e2e-тесты (`grep -r "data-device-version" e2e/ tests/`), чтобы не сломать чужие селекторы.
4. **Реальные Core Web Vitals.** Прогони Playwright (`mobile-chromium`, `mobile-webkit`) с throttling (Slow 4G / CPU throttle через `page.emulateNetworkConditions` или `context.route` + CDP) на `/playground` и на паре публичных страниц. Запиши LCP/CLS/INP/TBT в отчёт с числами, не с «стало быстрее на глаз».

### Приоритет 2 — доверяй, но проверь то, что аудит считает уже сделанным

Из раздела «Что уже реализовано в agent_work» в `AGENT_AUDIT.md`, самое важное для тебя — реально прогони эти сценарии в браузере:
- Мобильный live-статус (`role=log`/`aria-live`) в транскрипте — audit пункт про `ResponsiveMessageList.tsx:101` — проверь с включённым screen reader (VoiceOver/TalkBack эмуляцией или хотя бы вручную по aria-дереву), что не перечитывается весь архив на каждый токен ответа.

## Как вести ночь — порядок действий

Не трать всю ночь на чтение и не бросайся чинить первое найденное. Разумное деление:
1. **Первые ~20% времени** — быстрый систематический проход по своей зоне (список директорий выше) плюс запуск Playwright/dev-сервера, чтобы своими глазами увидеть текущее состояние на 320/360/390/414/430/768px. Зафиксируй находки списком (свой `AGENT_AUDIT_MOBILE.md`), прежде чем что-либо чинить — так же, как это сделал предыдущий агент.
2. **Основное время** — чини по приоритету выше, каждую правку — с локальным прогоном `npm run test:unit`/`test:integration` и визуальной проверкой в Playwright. Коммить часто, небольшими логичными шагами, с понятными сообщениями — не одним гигантским коммитом под утро.
3. **Последние ~15-20% времени** — полный регресс: весь `npm run check` кроме заведомо известного `trust:legal`; полный прогон Playwright на всех трёх мобильных/десктопных профилях (десктопный тоже — чтобы убедиться, что ты ничего не сломал Codex'у в общих файлах); написание отчёта.
